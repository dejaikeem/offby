# Offby — 무엇이고, 왜 필요하고, 누가 어떻게 쓰나

README가 "어떻게 동작하나"라면 이 문서는 "누구에게 무슨 쓸모인가"다. 개인 개발자, 코딩 에이전트 사용자, 게이트웨이를 운영하는 팀, Nebius Token Factory, 그리고 토큰을 파는 SaaS 일반 — 다섯 관점으로 나눴다. 숫자는 전부 이 저장소의 실측(`docs/experiments/`)이거나 2026-09-09 시장 조사에서 출처가 확인된 것이다.

## 1. 한 문단으로

Offby는 **LLM을 수천 번 부르는 무인 배치 작업 옆에 서는 미터기**다. 작업을 돌리기 전에 "콜 몇 번, 콜당 입력·출력 토큰 얼마쯤, 어느 모델"이라고 적어두면(예보), 작업의 요청이 Offby를 거쳐 나가면서 응답마다 붙어오는 토큰 수(`usage`)를 기록하고, 실측이 예보와 항목별로 확신 있게 어긋나면 — 예산이 바닥난 뒤가 아니라 초반 10여 콜에서 — 작업에 HTTP 402를 돌려줘 세우고 **어느 항목이 몇 배 틀렸는지, 왜인지**를 말해준다.

택시 미터기가 "지금 페이스면 9만 원인데, 예상과 다른 건 거리가 아니라 톨게이트 요금"이라고 말하고 차를 세우는 것과 같다. 작업 쪽에서 바꿀 건 환경변수 한 줄(`OPENAI_BASE_URL`)이고, 프롬프트나 답변은 저장하지 않는다.

**Offby는 지출을 줄이는 도구가 아니라 배치가 계획대로 끝나게 하는 도구다.** 고친 뒤의 run도 예보한 만큼의 돈을 쓴다. 그 돈은 폭주 → 중간에 죽임 → 환불 요청 → 다음 배치는 다른 곳으로, 가 됐을 돈이다.

## 2. 왜 필요한가 — 문제의 모양

### 2.1 배치 비용은 "얼마"가 아니라 "콜당 모양"에서 깨진다

배치 비용 = 콜 수 × (입력 토큰 × 단가 + 출력 토큰 × 단가). 이 네 항목 중 하나가 예상과 다르면 총액이 몇 배로 튄다. 그리고 그 "다름"은 청구서에 도착하기 훨씬 전에, 첫 10콜의 `usage`에 이미 들어 있다.

실제로 깨지는 항목은 늘 같은 다섯 가지다 — 2026년 사고 기록(63건 카탈로그, 벤더 포럼, 포스트모템)을 뜯으면 근원이 이 다섯에 1:1로 대응한다:

| 항목 | 깨지는 방식 | 실제 사례 |
|---|---|---|
| 출력 토큰 | 모델이 답하기 전에 "생각"을 하고 그 흔적이 출력으로 청구됨 | Gemini 2025-08 thinking 토큰 과금 버그, 청구 $70k+; 한 개발자 예상 $11 → 실제 $963 |
| 출력 토큰 | `max_tokens`를 안 걸어 답이 길어짐 / 걸어서 답이 잘림 | 로컬 런타임이 `enable_thinking=false`를 무시해 reasoning이 `max_tokens`를 다 먹고 답이 빈 문자열 |
| 콜 수 | 재시도 폭풍, 팬아웃 | 에이전트가 60초에 1,384콜, 사고당 $20~30 (OpenClaw 2026); 63건 중 재시도 루프 27건 |
| 단가 | 별칭이 다른 모델·다른 결제 경로로 감 | `claude-sonnet-5` vs `claude-sonnet-5-bedrock` — 같은 모델 이름, 다른 청구서 |
| usage 자체 | 게이트웨이가 `include_usage`를 무시해 비용이 안 보임 | 배치 usage는 결과 파일이나 청구서에서만 (OpenAI Batch $212, 결과 0건) |

### 2.2 캡은 늦고, 이유를 모른다

벤더와 게이트웨이의 안전장치는 **누적 달러**를 센다: 월별 키 예산(OpenAI·Anthropic·Google·Groq·Fireworks), 런 단위 달러 천장(Cloudflare AI Gateway 2026-06, LiteLLM 세션 예산, OpenRouter·Vercel 키별 한도). 전부 필요하고 Offby는 이들을 대체하지 않는다. 하지만 구조적으로 못 하는 게 둘 있다:

- **늦다.** 천장은 예상 비용 이상으로 잡아야 하므로 의도한 지출의 ~100%를 쓴 뒤에야 울린다. 출력이 8배면 "$20 소진, 19% 처리"에서 멈추고, 같은 설정으로 다시 돌리면 같은 일이 난다.
- **이유를 모른다.** "Current cost: 20.0, Max budget: 20". 콜 수·입력·출력·단가 중 뭐가 틀렸는지는 개념 자체가 없다.

이상 감지(AWS Cost Anomaly Detection, Datadog, FinOps 툴)는 12~30일의 이력이 필요해서 **오늘 처음 도는 배치**에는 기준선이 없다. Offby의 기준선은 사용자의 예보라 1콜부터 있다.

### 2.3 그래서 Offby가 하는 것, 딱 하나

**사용자가 말한 숫자와 청구서 숫자를 항목별로 대조해서, 돈이 나가기 전에 어긋난 항목의 이름을 부른다.** 예측 모델이 없다. 예보는 사용자(또는 사용자의 코드를 쓴 에이전트, 또는 지난 run)가 준 숫자이고, 실측은 응답에 공짜로 붙어오는 `usage`이고, 판정은 나눗셈과 확신 검정이다.

## 3. 어떻게 동작하나 (짧게)

```
내 배치 ──HTTP──▶ Offby 프록시 ──▶ 업스트림 (Token Factory / OpenAI / Ollama …)
                     │  응답은 그대로 통과. usage 숫자만 SQLite에 기록
                     │  유효 콜 10개부터: 항별 실측/예보 비율을 t > 2.5로 검정
                     └─ 이탈 → 다음 요청에 402 + "output_tokens 3.1x (60→185)" + 진단
```

- **예보** = 콜 수 · 입력 tok/콜 · 출력 tok/콜 · 단가 · 창. 출처: CLI 플래그, 에이전트가 코드에서 뽑은 값, 문장(nano가 파싱), 첫 N콜(베이스라인), 지난 run(로드맵).
- **판정** = 순수 산술. hot path에 모델 호출 0. 에러 응답과 usage 없는 응답은 콜로 세지 않고 따로 표시.
- **진단** = 이탈했을 때만, usage 숫자 묶음에서 산술로 뽑은 가설("청구된 토큰의 96%가 reasoning 흔적")을 큰 모델이 확인·반박.
- **lessons** = 잡 횡단 기억. "이 모델은 thinking이 출력을 4.6배로 만든다"를 다음 예보에 쓴다.

한계도 처음부터 적어둔다: 402는 이탈을 만든 콜의 *다음* 요청부터라 동시성만큼은 더 나간다. 그리고 확신 검정은 급변(3배 이상)엔 10~15콜, 살짝 넘는 지속적 초과(2~3배)엔 무력하다 — 야간 5,569콜 실험에서 2.2배 초과를 217콜 동안 통과시켰다(`docs/experiments/2026-09-10-overnight-30b/`). 누적 검정(CUSUM) 병행은 미결.

## 4. 누가 어떻게 쓰나

### 4.1 개인 개발자·연구자 — 키 하나, 노트북 하나

**상황.** 리뷰 20만 건 분류, 임베딩 1만 건, 프롬프트 1,000개 × 모델 3개 eval 스윕. 제공사 키 하나로 돌리고, 돌려놓고 잔다.

**지금 하는 것.** `max_tokens`를 걸고, 키에 월 캡을 걸고, 아침에 청구서를 본다. 캡이 울렸으면 절반 처리된 결과와 사라진 예산이 남는다.

**Offby로.**
```bash
offby job ensure nightly-classify --calls 200000 --input 400 --output 250 --model <id> --budget 20
OPENAI_BASE_URL=http://localhost:8402/j/nightly-classify/v1 python classify.py
```
10여 콜 뒤 402가 나면 `offby report`로 어느 항이 왜 틀렸는지 보고, 코드를 고치고, `offby accept`로 재개한다. 잡 이름을 고정해두면 다음 날 `job ensure`만 다시 불러 새 run이 되고, `lessons`가 모델별 배수를 기억한다.

**로컬 모델도 같다.** Ollama의 `/v1`을 업스트림으로 두면 비용 $0으로 같은 흐름을 검증할 수 있다. 실측(`docs/experiments/2026-09-09-local-nemotron/`): Nemotron 3 Nano 30B는 기본 thinking ON이고 같은 프롬프트에 56~4,000토큰을 낸다; thinking on/off 배수 4.3~4.6×; 출력을 60으로 잘못 예보한 run은 11콜에서 멈췄다($0.0006 지출).

**언제 안 맞나.** 사람이 보고 있는 인터랙티브 세션, 챗봇 트래픽, 콜마다 컨텍스트가 자라는 ReAct 루프. "콜당 모양이 대충 일정하다"가 성립하지 않으면 예보 대비 배수는 의미가 없다. 그땐 `--baseline`으로 급변만 잡거나, 쓰지 않는다.

### 4.2 코딩 에이전트로 일하는 사람 — 예보를 사람이 안 쓴다

배치 스크립트를 쓰는 건 이제 대개 Claude Code 같은 에이전트다. 그 에이전트는 방금 자기가 쓴 코드에 N(데이터 파일 행 수), 프롬프트 템플릿(입력 토큰), 모델 id를 전부 갖고 있다 — 사람이 문장으로 추측하는 것보다 정확한 예보를 만들 수 있다.

`skills/offby/SKILL.md`가 그 절차다: LLM 루프를 돌리기 직전에 발동 → `offby lessons`를 읽고 → 코드에서 5항을 뽑아 `job ensure` → 프록시로 실행 → 402면 `report`를 읽고 코드를 고쳐(예: thinking 끄기) 재실행 → 끝나면 사용자에게 "예보 vs 실측" 한 줄.

이 입구는 게이트웨이 예산이 못 갖는 것을 갖는다: **"예보는 누가 쓰나"에 대한 답.** 그리고 에이전트가 "네 가정이 8배 틀렸다"는 구조화된 에러를 받아 스스로 고치는 루프가 생긴다. 실측으로도 확인됐다 — 30B는 문장 파싱을 5항 전부 맞췄지만 4B는 "120 reviews"를 1건으로 읽었다. 코드에서 N을 세는 편이 문장 파싱보다 믿을 만하다.

### 4.3 게이트웨이를 운영하는 팀 — 캡 옆에 서는 층

**상황.** 회사가 모든 LLM 지출을 LiteLLM(또는 Portkey·Cloudflare AI Gateway) 하나로 묶고, 팀·개인별 virtual key에 월 예산을 건다. raw provider key는 감사를 벗어나므로 거부한다. 큰 지출은 eval 스윕과 "크레딧 만료 전에 태우기" 배치다.

**Offby가 대체하지 않는 것.** 키별 월 캡은 그대로 두는 게 맞다. 그건 스프링클러다.

**Offby가 보태는 것.** 런 단위 예보 대비 검정 = 연기 감지기. 다만 이 팀에는 **두 번째 프록시를 끼우는 게 아니라 게이트웨이 안에 심판을 넣는 형태**가 맞다: LiteLLM `CustomLogger`의 `async_post_call_success_hook`이 콜마다 `usage`를 보고, pre-call hook이 이탈 시 402를 낸다. 키 해시 + `metadata.tags: offby:<job>`로 잡을 식별하고, 게이트웨이가 이미 계산한 `response_cost`를 쓰면 가격 오라클도 필요 없다. 이게 로드맵 3주차의 "LiteLLM 플러그인 모드"다.

**팀이 얻는 것.** 폭주한 잡 하나가 팀 키 예산을 다 태워 남의 요청까지 거부되는 사고(캡의 구조적 문제)가 줄고, 사고가 나도 "어느 잡의 어느 항이 몇 배"가 로그에 남는다. 사이드카는 격리 네트워크 문제의 답이 **아니다** — 같은 업스트림 경로를 써야 한다.

### 4.4 Nebius Token Factory — 유저 관점과 Nebius 관점

**현황(2026-09-09 조사).** Token Factory에는 지출 캡이 없다(`billing threshold`는 자동 결제 트리거), 알림도 없고, 키별 usage는 아이디어 보드에 1년 넘게 "In Review", 관측 페이지는 스스로 "billing reconciliation용 아님"이라 적고, 레이트리밋은 15분마다 +20%씩 20배까지 자동 상향된다 — 폭주 중에 더 열어주는 구조다. 배치 작업은 도는 동안 토큰 수를 안 보여준다.

**Token Factory 유저에게.** Offby는 "더 정밀한 층"이 아니라 **유일한 층**이다. 사이드카로 띄우고 `OPENAI_BASE_URL`만 바꾸면 되고, `/v1/models`에 단가가 있으면 오라클이 읽는다. 특히 Nemotron 3는 기본 thinking ON이라 문단 답변을 예보하고 흔적까지 청구되는 게 정확히 README 시나리오다. 4B·30B 로컬 실측이 그 배수를 3.5~4.6×로 보여줬다.

**Nebius에게 — 토큰을 파는 회사가 왜 이걸 원하나.** 토큰 매출은 한 번의 폭주가 아니라 재방문에서 나온다. 폭주 청구서 뒤에 오는 건 환불 요청·차지백·지원 티켓·공개 불만이다(Gemini 환불, Bedrock $30k 기사). 그래서 OpenAI는 2026-07에 하드캡을 *복원*하며 "가장 많이 요청받은 기능"이라 했고, Google·Cloudflare·Vercel이 2026년에 캡을 냈다. 예측 가능해야 기업이 배치를 올린다. Offby가 Nebius에 주는 것은:

1. **분쟁 감소** — 폭주가 첫 10콜에서 서고, 사용자가 원인을 알고 고쳐서 *완주*한다. 환불 대신 매출.
2. **Nemotron을 잘 쓰는 법의 실측 데이터** — "thinking이 출력을 4.6배로 만든다, 손잡이는 `enable_thinking`" 같은 `lessons`는 NVIDIA가 문서에 쓰고 싶은 문장이지 숨기고 싶은 문장이 아니다. Nemotron 3에는 reasoning budget 제어가 *있다* — Offby는 그 손잡이를 잊었을 때 알려주는 도구다.
3. **플랫폼에 없는 층의 설계도** — 키별 캡, usage의 `reasoning_tokens`, 배치 중 토큰 노출. Offby와 함께 기능 요청으로 낸다. Nebius가 캡을 만들면 그건 기본 사양이고, Offby는 그 위의 층으로 남는다.

**해커톤 서사는 여기서 나온다.** "청구서를 깎아준다"가 아니라 **"Token Factory에 없는 층을 Token Factory를 위해 만들었다."** 데모는 halt가 아니라 alert 모드로 — "10콜에서 '출력이 4배, thinking 켜져 있음'이라고 알려줬고, 사용자가 끄고 완주했다."

### 4.5 serviced API를 파는 SaaS 일반 — 신뢰성 기능으로서의 "런 계약"

토큰·임베딩·벌크 추론 API를 파는 회사가 Offby의 아이디어를 **플랫폼 안에** 넣으면 어떤 모양이 되는가. 독립 프록시가 아니라 API 설계의 관점에서:

**(a) 런 계약(run contract).** 클라이언트가 run id와 예보(콜 수·콜당 입출력·모델·예산)를 선언하면 플랫폼이 첫 N콜에서 항별로 검정하고, 이탈 시 402 또는 경고 헤더를 돌려준다. 캡이 "얼마까지"라면 계약은 "어떤 모양으로". 둘은 겹치지 않는다.

**(b) 배치 제출 전 카나리.** Batch API는 한 번 제출하면 결과 파일이 올 때까지 usage가 안 보인다. 제출 전에 첫 10~20건을 동기로 돌려 예보 대비 모양을 확인하고, 통과하면 배치를 받는다. 지금은 어떤 벤더도 이걸 안 한다(OpenAI Batch $212, 결과 0건 사례).

**(c) reasoning 비중을 usage에 넣기.** `completion_tokens_details.reasoning_tokens`를 항상 채우면 "청구의 96%가 흔적"이라는 진단이 추정 없이 정확해진다. Ollama·다수 서빙 스택은 이걸 비워 두고, 그래서 Offby는 글자 수로 추정한다.

**(d) 이상 감지 신호.** 키 유출·오용은 "모양"이 먼저 깨진다 — 갑자기 다른 모델, 다른 입력 길이, 다른 콜 속도. 런 계약 대비 이탈은 달러 캡보다 이른 유출 신호다(Google 키 남용 사례: 분 단위로 $10k).

**(e) 지원 비용.** "왜 이렇게 나왔나"에 답할 수 있는 로그가 남는다: 어느 잡, 어느 항, 몇 배, 어느 모델. 환불 심사와 고객 대화가 짧아진다.

**(f) 문서화 자산.** 모델별 thinking on/off 배수, 프롬프트 유형별 출력 분포(σ, p95)는 사용자에게 가장 필요한 숫자인데 아무 벤더도 공개하지 않는다. `lessons`의 집계판이 그 자리다.

이 여섯 가지에 공통된 사업 논리는 하나다: **예측 가능한 플랫폼이 더 많은 무인 워크로드를 받는다.** 캡을 스스로 만드는 벤더들이 이미 그 논리로 움직이고 있다.

## 5. 하지 않는 것

- 지출을 줄이지 않는다 — 계획대로 끝나게 한다.
- 캡을 대체하지 않는다 — 옆에 선다.
- 인터랙티브 사용에 끼우지 않는다 — 사람이 이미 루프 안에 있다.
- 프롬프트·답변을 저장하지 않는다 — usage만.
- 콜이 커밋되기 전엔 못 막는다 — 402는 다음 요청부터.
- 살짝 넘는 지속적 초과(2~3배)는 지금 규칙으론 못 잡는다 — 미결.

## 6. 근거

| 주장 | 근거 |
|---|---|
| Nemotron 3는 기본 thinking ON | 공식 chat template `enable_thinking=True`; 로컬 4B·30B 실측 |
| thinking이 출력을 3.5~4.6배로 | 4B 3.5× / 30B 4.3~4.6× (`docs/experiments/2026-09-09-local-nemotron/`) |
| 출력 분포는 꼬리가 길다 | 같은 프롬프트에 56~4,000토큰, σ≈0.8~0.9; p95가 중앙값의 6~10배 |
| 건강한 배치를 안 멈춘다 | 야간 1,351콜, 4,000토큰 컷 23건 섞여도 오탐 0 (`2026-09-10-overnight-30b/`) |
| 잘못 예보한 run은 초반에 선다 | 출력 60 오예보: 30B 11콜·4B 42콜, 지출 $0.0006~0.003 |
| 지속적 경미 초과는 못 잡는다 | 야간 Phase B: 2.2배를 217콜 동안 통과 (CUSUM이면 168콜) |
| 아무 벤더도 런 예보를 항별로 검정하지 않는다 | 2026-09-09 조사: 제공사 12·게이트웨이 10·배치 플랫폼·FinOps (`notes/2026-09-09-market-survey.md`, 로컬) |
| Token Factory엔 캡·알림이 없다 | Nebius 문서 billing/rate-limits/observability, 아이디어 보드 |
| 통증은 반복적이다 | Gemini $70k+, Bedrock $30k, OpenAI Batch $212, OpenClaw 60초 1,384콜, arXiv 63건 |
